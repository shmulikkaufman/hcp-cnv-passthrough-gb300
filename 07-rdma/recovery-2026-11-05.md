## Two distinct bugs

### Device-plugin endpoint collision

The original shim used `bf3-shim.sock` for every resource. BF-3 and CX-8
instances on a worker therefore unlinked each other's socket. The updated
source derives a deterministic endpoint from the resource-name SHA-256.
It also rejects requests for unadvertised or non-vfio-bound devices.

Only CX-8 binaries were updated, at `/var/local/cx8-shim/device-plugin`;
the existing BF-3 binaries were left unchanged. Tests cover endpoint
isolation, multiple-device allocation, and unknown-device rejection:

```bash
cd 07-rdma/bf3-shim
go test -race ./...
go vet ./...
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags='-s -w' -o bf3-shim .
```

### Overlapping guest PCI bus ranges

Actual QEMU errors included `Bus 249 is already in use` and `Bus 250 is
already in use`. Some generated layouts used distinct expander start
numbers but still overlapped child root-port bus ranges. One failing
two-NIC layout had ranges `249-251`, `252-253`, and `250-251`.

This is a topology-generation failure, **not a proven BAR-capacity limit
or a hardware limit on NIC count**. Low QEMU CPU time or a missing guest
agent alone was insufficient evidence for the earlier firmware diagnosis.
Later IOMMUFD errors followed failed start attempts; they did not establish
the primary cause. The exact upstream allocator defect/fix is not identified.

## Narrow, per-VM workaround

`pci_bus_guard.py` is an OnDefineDomain hook using the stock, digest-pinned
CNV sidecar-shim image. It calculates each expander's required bus range
from its child PCI bridges. If ranges overlap, it allocates disjoint ranges
downward from bus 255. It changes **only `target/@busNr` values**, preserving
all other XML bytes: device bindings, controller indices, NUMA nodes, GPU
generic initiators, memory/MMIO sizes, disks and firmware remain intact.

This is a **lab workaround**, not an asserted supported upstream fix. It is
not the older MMIO hook that was harmful to CNV 4.22. Unit tests cover one,
two and four NIC layouts, duplicate starts, child-range overlap, and valid
layouts left unchanged. It was also checked against captured actual VM3 and
VM12 XML before deployment. The stock image's Python interpreter was verified
in a short-lived unprivileged pod, which was then removed.

```bash
cd 07-rdma
python3 -m unittest -v test_pci_bus_guard.py
```

VM12's hook log showed `250-251 -> 254-255` for the overlapping controller;
the resulting expanders started at 254, 252 and 250. Its guest booted,
SSH returned, the VF reached ACTIVE, and NVIDIA devices remained visible.
VM3 was then changed separately and passed the same guest-boot checks.

The ConfigMap is `gpu-vm-test/pci-expander-bus-guard`. A reproducible merge
patch is in `09-cx8-baseline.patch.yaml`. Apply it only after inspecting
existing hook and device settings, while the selected VM is stopped.

## Boundaries and next steps

- Two- and four-rail throughput is **not** revalidated here. Do not describe
  the current guest configuration as four NICs or a bonded 1.6 Tb/s link.
- Linux Ethernet bonding/ECMP is not automatically RoCE multi-rail or LAG.
  Validate vendor/guest-VF support and the physical fabric before choosing
  aggregation; application-aware multi-rail is a separate option.
- Physical NIC/GPU locality must be discovered from actual allocations.
  Four arbitrary PFs spanning four GPU roots are not necessarily two
  correctly aligned planes for each of the two assigned GPUs.
- Do not assume an RDMA MTU of 8192: common verbs MTU enums stop at 4096.
  Jumbo Ethernet support and attainable throughput must be measured, not
  inferred from a failed jumbo ping while local MTU is still 1500.
- VF provisioning on the CX-8 rail was originally performed manually, and
  the test IPs are runtime-only. Automatic host/guest reboot recovery is not
  qualified by these tests. No node reboot, jumbo-MTU change, bond, or switch
  configuration was performed in this recovery.
- Rollback if a future hook change fails: halt the affected VM; restore its
  saved template; remove the hook annotation and NIC hostDevices for the
  known-bootable GPU-only fallback; then start and verify SSH. Preserve the
  existing DataVolume/PVC and firmware identity. Removing the hook while
  retaining NICs can reintroduce the PCI collision.
